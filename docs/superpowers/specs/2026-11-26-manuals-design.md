## 1. 背景与目标

现有文档覆盖了「为什么做」（白皮书）、「是什么、怎么起服务」（README）、「前后端怎么接」（FRONTEND / SPEC-frontend-wiring）、「验收到不到位」（selftest-v32）。**唯独缺一层：一线用户打开界面时，某个屏到底怎么用。**

这一层对「好用」最要紧——用户不是来读架构的，是来问「我现在该点哪儿」。所以补一套 `docs/manuals/`，按功能模块写操作手册，每篇回答五个问题：**它解决什么、你在哪、一步步怎么点、为什么会卡住、怎么回账本核对。**（前四点讲操作，第五点教他不信任何人也能自己验。）

**目标（可判定的成功标准）：**

1. BA / PA / DA / SA 任一角色，不读源码、不问人，能照着对应篇目把该角色的事从头做一遍。
2. 手册里的按钮文案、视图名、账本事实名与当前代码一致；**跑一次 `node docs/manuals/check.cjs` 就能发现漂移**，不必等到有人照着不存在的按钮点空。
3. 每篇模块正文配真实界面截图（明主题），截图可一键重拍。

**非目标（YAGNI）：**

- 不做从代码自动生成手册（抽出来的没有温度）。
- 不重抄白皮书的设计论述、不重抄 README 的起服务步骤，只引用。
- 不做多语言、不做面向外部客户的公开站点。

## 2. 读者与角色

角色与权限来自 `internal/bff/session.go` 的 `roleActs`；下表活动范围已逐条对照后端 `Require(...)` 核实。

| 角色 | 在系统里**能**干什么（已核实） | 主要读哪几篇 |
|---|---|---|
| **BA 业务** | 写 BRD（`brd`）、维护需求池（`backlog`）、验收判定「通过/不提过」（`acceptAT`）、派知识库问题单给 owner（`brd`） | 00 / 01（只读，看结构）/ 02 / 03 / 07（验收判定部分） |
| **PA 产品** | 建工作空间/项目/交付单元（`pbc`）、编辑原型与方案制品草稿（`acceptProto`）、方案沉淀（`store`）、看 Agent 定义 | 00 / 01 / 04 / 05 / 09 |
| **DA 交付** | 发起交付、跑构建与测试（`build`/`test`）、部署（`deploy`）、看编排与真产物 | 00 / 06 / 09 |
| **SA 系统** | 打 tag 与发布批次（`tag`）、配置（`config`）、**发布 Agent 新版本（也是 `tag`）** | 00 / 07（打 tag 部分）/ 08 / 09 / 11 |
| **全角色** | 通知中心（只读投影，无权限门） | 10 |

> **三个容易写错的地方，均已在代码里确认：**
> 1. **建单元不是 BA 的事**——`createUnit` 要求 `ActPbc`（`v23.go:200`），只有 PA 有。BA 只写 BRD（`brd`）与需求池（`backlog`）。
> 2. **07 篇跨两个人**——「通过 / 不提过」要 `acceptAT`，只有 BA；「打 tag 固化交付物」要 `tag`，只有 SA。手册必须分开写并交代交接点。
> 3. **09 篇的「发布新版本」也是 SA**——`agentPublish` 要求 `ActTag`（`v23.go:531`）。所以 09 的读者里必须有 SA，否则读的人点下去只有 403。

**关于 14 个文件的覆盖：** 模块正文 01~11 全部被至少一个角色读到；`00-快速上手` 是四角色共同起点；`10-通知中心` 是全角色；`README.md` 是索引、`附录-术语与权限矩阵.md` 是查询表，二者**面向所有读者，不归某个角色**——这不是覆盖漏洞，是辅助页的固有属性。

## 4. 单篇骨架（五段式，仅适用于 01~11 模块正文篇）

```markdown
# 07 验证与打 tag

## 它解决什么
（3-5 句讲人话。要点出：验收判定是 BA 的，打 tag 是 SA 的——两个人、两个动作。）

## 你在哪
（侧栏 → 单元「交付质检 Agent」→ 验证。配 shots/07-verify-tag.png（BA 视角）
 与 shots/07-tag-sa.png（SA 视角，打 tag 按钮可用态）。）

## 怎么做
**BA 做验收判定：**
1. 左边一排 AC chip，点一条切换当前验收对象；
2. PBC 走真机操作（筛账期、勾选、批量生成），Agent 走对话验收（真发一句话）；
3. 不过 → 点「不提过」，bug 标题预填、复现步骤自动带入，提交后进 backlog；
4. 修完这一条可重验，其它条不受影响。

**交接：** 验收清单全过、HEAD 有 digest、测试全过之后，交给 SA。

**SA 打 tag：**
5. 点「打 tag 固化交付物」。它只认当前 HEAD。

## 会卡在哪
（下面每条都是真实的拦截文案，照抄代码）
- 「还差 N 条验收未通过」——页面显示（`VerifyView.vue:53`）；服务端报错带分数：
  「还差 N 条验收未通过（x/y），不能打 tag」（`release.go:123`）。
- 「HEAD vX.Y 没有构建 digest，先构建」；「HEAD vX.Y 没有对应的测试结果」；
  「测试未全过（x/y），不能打 tag」。
- 「HEAD vX.Y 已经打过 tag vA.B」——一个 HEAD 只能一个 tag。
- 打 tag 前 HEAD 无提交：「还没有提交，无法打 tag」。

> 注意：手册**不要**写「点『重新测试』按钮」——界面没有这个入口；
> 重跑测试只有 DA 通过 `POST /api/items/{id}/run` 发起。

## 怎么核对
查 `check.decided`、`defect.created`、`tag.created`。
「通过条数」= 对每个 AC **取最后一次** `check.decided` 里为 pass 的数量
（同一条可以重验多次，不能直接数 pass 事实的条数）。
```

**写作硬规矩：**

- **按钮与提示文案照抄代码**，一字不改。
- **涉及权限的步骤必须标清是谁的动作**（BA / PA / DA / SA），跨角色页写明交接点。
- **界面里没有的动作不许写**（对照 §3.1）。
- 每篇末尾带守卫块（§6）；截图统一明主题；篇间只做相对链接，不复制内容。

## 6. 准确性守卫（check.cjs）

**目的：** 让文档漂移在跑一次脚本时就暴露，而不是半年后有人照着不存在的按钮点空。

**形式：** `docs/manuals/check.cjs`，Node、零第三方依赖、只读文件。

**守卫块**（HTML 注释，渲染不可见）：

```markdown
<!-- guard
views: verify
buttons: 打 tag 固化交付物 | 不提过
prompts: 还差 | 没有构建 digest，先构建 | 已经打过 tag
facts: check.decided | defect.created | tag.created
shots: 07-verify-tag.png | 07-tag-sa.png
-->
```

**检查项：**

| # | 检查 | 数据来源 | 判据 |
|---|---|---|---|
| 1 | 11 篇模块正文各含五个必需二级标题，顺序一致 | 解析 md | 缺段/顺序错 → 报错 |
| 2 | `views:` 每个视图键存在 | `App.vue` 的 `VIEWS` | 不存在 → 报错 |
| 3 | `buttons:` / `prompts:` 每条文案能在前端源码里找到 | **`web/src/**`（含 `.vue` 模板与 `<script setup>` 字符串、`App.vue` 导航文案）** | 找不到 → 报错 |
| 4 | `facts:` 每个事实 kind 存在于后端 | `internal/**` 字符串字面量 | 未定义 → 报错 |
| 5 | `shots:` 每张图存在 | `docs/manuals/shots/` | 缺失 → 报错 |
| 6 | md 里相对链接目标存在 | 文件系统 | 失效 → 报错 |
| 7 | 守卫块结构合法 | 解析块 | 见下 |
| 8 | **固定 14 个文件存在且文件名与本设计 §3 一致** | 文件系统 | 缺文件/改名 → 报错 |

> 第 3 条把「提示语」纳入自动检查（多数 toast 是 `<script setup>` 里的字符串，只查模板会漏）；第 8 条补上 §8 验收第 1 条此前无守卫的漏洞。

**防误命中：** <4 字的通用词（如 `通过`，会被「通过率」「已通过」命中）不得单独作锚点，只告警不通过；必须换成足够长的唯一字面量。

**守卫块异常处理（明确定义）：**

| 情形 | 处置 |
|---|---|
| 模块正文缺守卫块 | 报错 |
| 块格式坏（缺 `-->`、键名非法、空块 `<!-- guard -->`） | 报错，指明文件与行 |
| 同一块重复键 | 报错 |
| 未知键（如 `button:` 拼错） | 告警，不阻断 |
| **必需键缺失**（`views`/`buttons`/`facts`/`shots` 四者中缺任一） | 报错；值为 `-` 表示"本页确实没有"，避免用空值蒙混 |
| 辅助篇无守卫块 | 跳过 |

**契约：**

- 通过：`manuals: OK (11 篇模块正文 + 3 辅助篇)`，退出码 0。
- 失败：逐条 `文件:行 → 问题`，退出码 1。

**已知边界：** 这是**字面量存在性**检查，不是语义检查——能发现「按钮改名了」，发现不了「步骤顺序写反了」。语义正确性仍靠人工评审（§8）。

## 8. 验收标准

1. 14 个 md 全部存在且文件名与 §3 一致；11 篇模块正文各自五段齐全；`node docs/manuals/check.cjs` 退出码 0（第 8 条检查直接覆盖文件存在性）。
2. 11 篇模块正文各≥1 张真实明主题截图，可由 `shots_manual.cjs` 重拍复现；07 篇必须有 BA 与 SA 两个可用态。
3. **四个角色各抽一人**，每人仅凭手册完成自己角色的主流程，不查阅源码。
   - **必须在同一份干净账本上、按依赖顺序走**：PA 建项目→BA 写 BRD/建工作项→DA 发起交付→BA 验收判定→SA 打 tag 发布。
   - 起服务用 `SEED_DEMO=1` + 新 `LEDGER_PREFIX`（仓库 CLAUDE.md 已警告：脏账本或第二轮会重名重号）。
4. README「文档」表加一行指向 `docs/manuals/README.md`；`CLAUDE.md` 的**「文档」小节**加索引行，**「验证」小节**加入 `node docs/manuals/check.cjs`。
5. 守卫反向验证：故意改错一处按钮文案，`check.cjs` 必须失败。

## 9. 风险与对策

| 风险 | 对策 |
