## 1. 背景与目标

现有文档覆盖了「为什么做」（白皮书）、「是什么、怎么起服务」（README）、「前后端怎么接」（FRONTEND / SPEC-frontend-wiring）、「验收到不到位」（selftest-v32）。**唯独缺一层：一线用户打开界面时，某个屏到底怎么用。**

这一层对「好用」最要紧——用户不是来读架构的，是来问「我现在该点哪儿」。所以补一套 `docs/manuals/`，按功能模块写操作手册，每篇回答四件事：**你在哪、要达成什么、一步步怎么点、为什么会卡住。**

**目标（可判定的成功标准）：**

1. BA / PA / DA / SA 任一角色，不读源码、不问人，能照着对应篇目把该角色的事从头做一遍。
2. 手册里的按钮文案、提示语、阶段名、账本事实名，与当前代码一致；界面漂移时能在当天被守卫脚本发现，而不是静默烂掉。
3. 每篇配真实界面截图（明主题），截图可一键重拍。

**非目标（YAGNI）：**

- 不做从代码自动生成手册（抽出来的没有温度）。
- 不重抄白皮书的设计论述、不重抄 README 的起服务步骤，只引用。
- 不做多语言、不做面向外部客户的公开站点。

## 4. 单篇骨架（五段式）

每篇正文固定五个二级标题，顺序不变：

```markdown
# 07 验证与打 tag

## 它解决什么
（3-5 句。为什么这个模块存在、它替人挡掉了什么。讲人话，不堆术语。）

## 你在哪
（导航路径：侧栏 → 单元「交付质检 Agent」→ 验证。配一张 shots/07-verify-tag.png。）

## 怎么做
1. 左边一排 AC chip，点一条切换当前验收对象；
2. PBC 走真机操作（筛账期、勾选、批量生成），Agent 走对话验收（真发一句话）；
3. 任一不过 → 点「不提过」，bug 标题预填、复现步骤自动带入，提交后进 backlog；
4. 全部通过且测试条数对得上 → 点「打 tag 固化交付物」。

## 会卡在哪
- 还差 N 条验收未通过 → 打不动，页面点名「还差 N 条验收未通过（x/y）」。
- 测试条数与当前 HEAD 不匹配 → 先重跑测试，再打 tag。
- tag 只认 HEAD：给历史提交打 tag 会失败并提示。

## 怎么核对
去账本查 `check.decided`、`defect.created`、`tag.created` 三条事实；
「验证页看到的通过条数」应等于 `check.decided` 里 `pass` 的数量。
```

**写作硬规矩：**

- **按钮与提示文案照抄代码**，一字不改（`打 tag 固化交付物` 而非「打tag」）。守卫会核对这些字面量。
- 每篇结尾带一个 HTML 注释的**守卫块**（见 §6），列出本页引用的视图键、按钮文案、账本事实、截图。
- 截图统一明主题，图注一句话说明「这张图你要看的是哪里」。
- 篇与篇之间只做相对链接引用，不复制对方的内容。

## 6. 准确性守卫（check.cjs）

**目的：** 让文档漂移在发生的当天暴露，而不是半年后有人照着不存在的按钮点。

**形式：** `docs/manuals/check.cjs`，Node、零第三方依赖，读文件即可（不启服务、不连账本）。

**每篇手册末尾的守卫块**（HTML 注释，渲染时不可见，读者无感）：

```markdown
<!-- guard
views: verify
buttons: 打 tag 固化交付物 | 不提过 | 通过
facts: check.decided | defect.created | tag.created
shots: 07-verify-tag.png
-->
```

**check.cjs 的检查项：**

| # | 检查 | 数据来源 | 失败即报错 |
|---|---|---|---|
| 1 | 每篇含五个必需二级标题 | 解析 md | 「07 缺「会卡在哪」段」 |
| 2 | `views:` 里的每个视图键存在 | `web/src/App.vue` 的 `VIEWS` 映射 + `web/src/views/*.vue` | 「视图 `verify` 不存在」 |
| 3 | `buttons:` 里每条文案能在前端模板里找到 | `web/src/views/*.vue`、`web/src/components/*.vue` 的模板文本 | 「按钮文案「打 tag 固化」在界面里找不到」 |
| 4 | `facts:` 里每个事实 kind 存在于后端 | `internal/` 里的字符串字面量集合 | 「事实 `tag.createdX` 未定义」 |
| 5 | `shots:` 里每张图存在 | `docs/manuals/shots/` | 「截图 07-verify-tag.png 缺失」 |
| 6 | md 里所有相对链接目标存在 | 文件系统 | 「链接 ../EXECUTION.md 失效」 |

**契约：**

- 通过：打印 `manuals: OK (13 篇)`，退出码 0。
- 失败：逐条列出 `文件:行 → 问题`，退出码 1。
- 调用方式：`node docs/manuals/check.cjs`；写进 CLAUDE.md 的「验证」小节，作为**改动前端界面后的自检项**，不进主验收（不拖慢 133 项）。

**已知边界（如实写明）：** 这是**字面量存在性**检查，不是语义检查——它能发现「按钮改名了」，发现不了「步骤顺序写反了」。语义正确性仍靠人工评审（§8 的验收）。

## 8. 验收标准（整套手册算「做完且不烂」的判据）

1. 13 篇 md 全部存在，每篇五段齐全，`node docs/manuals/check.cjs` 退出码 0。
2. 每篇至少一张真实明主题截图，且能通过 `shots_manual.cjs` 重拍复现。
3. 抽查三人（各挑一个角色路径）能仅凭手册完成该角色的主流程，不查阅源码。
4. README 顶部"文档"表增加一行指向 `docs/manuals/README.md`；CLAUDE.md 文档小节同步。
5. 守卫脚本在故意改错一处按钮文案时能失败（用一次反向验证证明守卫有效）。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 手册写完就烂 | §6 守卫 + §8 第 5 条反向验证 |
| 与白皮书/README 内容重复打架 | §7 分工表，手册只做「怎么用」 |
| 截图画质/主题不一致 | 复用已验证的明主题 addInitScript 写法，统一脚本产出 |
| 守卫过度拟合、误报 | 只查字面量存在性，条目从代码实时 grep，不硬编码清单 |
| 篇幅失控 | 每篇只回答五段，宁短勿全，细节留给截图 |

## 10. 落地顺序（交 writing-plans 细化）

1. 先写 `docs/manuals/README.md` + `附录`（定导航与术语），再写 `00-快速上手`（验证整体骨架）。
2. 写 `shots_manual.cjs` 并产出一批图。
3. 按角色路径成批写 01~11，每批写完跑一次 `check.cjs`。
4. 把 `check.cjs` 与文档索引接进 README / CLAUDE.md，做一次反向验证收尾。
